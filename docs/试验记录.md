## 试验 001 · 方案 A（干净 Chrome + 零接触登录）

- **目的**：验证"强制直连 + 登录期间不挂自动化协议"能否正常跳转
- **变量**：
  - 启动：手动拉起系统 Chrome，独立 profile `./profile`
  - 网络：`--no-proxy-server` 强制直连
  - 自动化：登录期间 **零 CDP 会话**，仅 HTTP 轮询 `/json/list`
- **预期**：扫码确认后 5–10 秒内，标签页 URL 从 `/login.html` 变为 `/platform/home`
- **结果**：✅ **成功**

### 实测时间线

```
10:06:39  LOGIN     https://channels.weixin.qq.com/login.html
10:07:51  PLATFORM  https://channels.weixin.qq.com/platform/home
```

耗时约 72 秒（含人工扫码确认）。登录后 DOM 读到真实账号数据：
视频号 ID `sphgyM4ssrETwB8`、关注者 238 —— 不是空壳页面。

### 结论

1. **出口 IP 就是真凶**。同一台机器、同一个 Chrome、同样的自动化介入程度，
   唯一实质性变化是 `--no-proxy-server`（出口从香港机房 42.200.231.106 变回家宽 111.60.73.11），
   登录即成功跳转。此前"扫码成功但不跳转"应归因于跨境机房 IP 触发风控。
2. `navigator.webdriver = false` 已实测确认，干净启动方案有效。
3. 不需要 Patchright、不需要改 UA、不需要注入伪装脚本。

## 试验 003 · 换账号（169 条视频）后的全量验证

- **目的**：换一个数据量大的账号，验证「列表全量加载 / 跨年时间 / 回复折叠 / 点开的是哪条视频」
- **结果**：✅ 全部跑通（修掉 4 个真 bug、纠正 1 个错误结论）

### 账号规模（运行时读到的，非写死）

| 项 | 值 |
|---|---|
| 视频总数 | `共169个`（页面文案），实测加载到 169/169 |
| 时间跨度 | 2026/10/21 07:05 → 2025/09/06 10:45 |
| 年份分布 | 2025 年 47 条，2026 年 122 条 |
| 时间格式（列表） | `2026/10/21 07:05`（带年份，跨年可直接用） |
| 时间格式（详情头） | `2026年10月21日 07:05`（同一条视频，**格式不同**） |

列表时间从新到旧严格递减，本次无逆序（暂无置顶打乱）。序号一律按 DOM 顺序，**不按时间重排**。

### 坑 1：窗口不可见 → 懒加载静默挂起（本次最关键发现）

| 现象 | 真相 |
|---|---|
| 列表滚不动，一直停在 10 / 20 / 30 条 | `document.visibilityState === "hidden"`（窗口最小化或被切到后台）时，页面滚动**不触发**懒加载。加载动画 `.loadmore__dot` 一直 `inline-flex` 在转，但请求不发 |
| 表现忽好忽坏 | 取决于窗口当时是否可见，与限流无关 |
| 解决 | CDP `Page.bringToFront` 即可让 `visibilityState` 变 `visible`（并拿到焦点），**不需要** PowerShell 去 `ShowWindow` 恢复窗口 |

`lib/cdp.js` 为此加了 `ensureVisible(send)`，`04 / 05 / 06` 开头都会调用，失败时抛出明确错误。

### 坑 2：已经在底部时，再设 `scrollTop = scrollHeight` 是空操作

容器贴底后重新赋值不产生 `scroll` 事件，因此不会触发下一批。表现为「前几轮能加载，之后就永远不动」。

解法：每轮先回退 400px 制造位移，再滚到底。`04 / 06` 都已改成 `SCROLL_NUDGE → SCROLL`（或 `SCROLL_BOTTOM`）两步。

### 坑 3：折叠回复不展开会误判「作者未回复」

- 折叠控件是 `.load-more__btn`，文案是 **「展开更多回复」**
- 早期按「查看更多 N 条回复」猜的文案**匹配不到**，会漏掉整串回复
- 该视频 76 条评论里有 3 处折叠，展开后 44 一级 + 32 回复 = 76，与页面声明一致
- `06` 已改为「滚动 → 展开 → 再滚动」交替执行，直到 `.load-more__btn` 归零

> 试验 005 修正：点击监听其实挂在父层 `.load-more`，且加载中再点会被组件忽略。
> 点 `.load-more__btn` 只在部分情况有效，详见试验 005 的 5.1 节。

### 坑 4：点开视频后，旧视频的评论还挂在 DOM 上

`05` 之前用「出现 `.comment-item`」判就绪，结果点第 2 条时读到的是**上一条视频残留的 76 条**，却打印「已就绪」。

实测切换过程（160ms 采样）：

```
点击前   n=4   tips=共 4 条评论   active=2
   0ms   n=4   tips=null          active=3   ← 评论区整体卸载
 160ms   n=0   tips=null          active=3
 480ms   n=11  tips=共 11 条评论  active=3   ← 新数据到位
```

**正确解法（比指纹比对更硬）**：详情区顶部有 `.feed-selected-info`，里面就是当前视频的 `.feed-title` + `.feed-time`。它和列表项用的是同一个类名，所以取列表时必须限定在 `.comment-feed-wrap` 内，否则会多算一条。

现在 `05` 的判据是：**详情头部的「标题+时间」与目标一致**（时间先归一化两种格式），才算点对了；之后再等评论区挂载。`06` 输出里也会带上当前视频的标题/时间，便于事后核对。

### 坑 5：列表里的「评论数」不可信，只能当参考

| 视频 | 列表显示 | 评论区实际 |
|---|---|---|
| 第 9 条 | 74 | 76 |
| 第 1 条 | 21 | 23 |
| 第 4 条 | 14 | 13 |

会涨（实时新评论）也会跌（删除/审核中）。**唯一权威数字是评论区的「共 N 条评论」**，`06` 以它对账。

### 坑 6：0 评论的视频，连「共 N 条评论」都不存在

- 有评论时：`.comment-count__tips` 显示「共 76 条评论」
- 0 评论时：**`.comment-count__tips` 整个不存在**，只有 `.feed-comment__wrp` 里一句「暂无评论」，
  且没有 `.comment-empty` 之类的专用元素

早期 `05` 用「tips 存在」判断「评论区已挂载」，碰到 0 评论视频会误报「评论未渲染」。
现在的判据：`tips 存在` **或** `容器文本含「暂无评论」` 且条数为 0。

该账号 169 条里有 4 条 0 评论（第 18 / 124 / 139 / 153 条），已实测通过。

## 试验 005 · 导航重写、随机跳页、展开回复修复

- **目的**：把「用户随口说一句读第 N 条」做成真正稳的端到端流程：
  换起点（任意菜单页 / 直接改地址）、换序号、评论区偶发卡死时都能自己恢复
- **结果**：✅ 随机回归 8/8 + 6/6；修掉 5 个真 bug

### 5.1 最关键的一个：第 169 条只读到 63/69

**现象**：页面声明 `共 69 条评论`，DOM 只有 63 个 `.comment-item`，且已经滚到底。
缺的 6 条不在懒加载队列里。

**排查链**（每一步都留了脚本）：

| 步骤 | 脚本 | 发现 |
|---|---|---|
| 1 | `probe-comments-stall.js` | 63 条、已贴底、`visible`+`focus=true`；剩 3 个「展开更多回复」 |
| 2 | `probe-expand.js` | 点 `.load-more__btn` 的几何中心，条数不变；DOM `.click()` 也不变 |
| 3 | `probe-expand-hit.js` | 命中栈是 `span → .load-more__btn → .load-more → .comment-item`，没被遮挡 |
| 4 | `probe-expand-listeners.js` | `.load-more__btn` 上 **0 个**监听；`.load-more` 上有 2 个 click |
| 5 | `probe-expand-capture.js` | CDP 真实点击的事件链完整（`isTrusted=true`），确实到达按钮 |
| 6 | `probe-bundle-remote.js` | 在 `async/251.*.js` 里找到 `handleReplyLoad` |

前端代码（`data/probe/js/async_251.9a7999b0.js`）：

```js
async handleReplyLoad(e, t) {
  if (-1 !== this.showReplyLoadingIndex) return;   // ← 加载中直接忽略后续点击
  this.showReplyLoadingIndex = t;
  let o = await this.store.fetchReply(e);
  o && o.comment && o.comment.length > 0 && (this.showReplyLoadingIndex = -1)
}
```

**根因**：

1. 点击监听挂在 `.load-more`（父层），不在 `.load-more__btn`；点在文字/图标之间的空隙就落空；
2. 点一次只加载**一条线程**的 2~3 条回复，不是全部；
3. 有线程正在加载时（`img.infinite-spin`），后续点击被 `showReplyLoadingIndex !== -1` 直接吞掉；
4. 接口返回空时 `showReplyLoadingIndex` 永不复位 → 转圈永久卡死，只能重载页面。

**修复**（`06-extract-comments.js` 的 `FIND_LOAD_MORE`）：

1. 只找「箭头态」`.load-more`（有 `.weui-icon-outlined-arrow`、无 `img`）；
2. `scrollIntoView({block:"center"})` 后，点 **`.load-more` 矩形中心**（真实 CDP 点击）；
3. 每点一次等 7s，看 `.comment-item` 是否增长；增长才继续下一个；
4. 只有转圈态时等 8s，两次无果就停止展开；
5. 点击失败 3 次后停止展开，避免死循环。

**效果**：第 169 条 63/69 → **69/69**（展开 3 处，5.4s）。

`07` 同时加了恢复层：`06` 抓到 `total < declared` 时整页重载、重跑 05+06 一次，序号不变。

### 5.2 导航重写：侧边栏只有图标

当前版本 `innerText` 为空、只有 `textContent`，顶层图标 56×56，悬停才弹菜单。

`lib/nav.js`：

- 先按 `textContent` 找（兼容旧版内联文字）；
- 失败则逐个悬停图标，轮询 `.finder-ui-desktop-menu__popup_menu` 的标题；
- 点完不算成功，要等 URL 变化或目标页渲染。

**坑**：顶层项过滤原本只排除 `.finder-ui-desktop-sub-menu`。
但在图文列表页（`/platform/post/finderNewLifePostList`），子项**直接挂在 popup 里**，

## 试验 012 · 回复按钮被页脚盖住：坐标点击失效（2026-10-24 16:10）

## 试验 017 · 第二轮盲评：未知事实不再“帮你确认”（2026-10-25）

### 规则变化

- 旧：业务未知 → `幫你確認下，私訊傾 📩`
- 新：业务相关但事实未列明 → **直接自信承接 + 引私域**：`呢個私訊我，幫你睇清楚 📩`
- 只有完全不相关、敏感/引战、纯表情/纯负面才不回。
- 纯捧场不加引导；是/否问题先答；`唔設門檻` 是核准口径，不算承诺。

### 结果（同一批 30 条）

| 指标 | 第一轮 B | 第二轮 B |
|---|---|---|
| 胜出 | 16 | **24** |
| 平手 | 12 | 5 |
| 模板 A 胜 | 2 | 1 |
| 回答问题 | 4.13 | **4.40** |
| 自然度 | 4.03 | **4.40** |
| 事实依据 | 4.57 | 3.93（评审把“唔設門檻”误判为承诺） |

- 不算平手：B 胜 24/25 = **96%**
- 算平手：B 不败 29/30 = **97%**

### 结论

- 新规则明显更像专业销售：不再说“帮你确认”，直接引私域。
- 下一轮要先修评审口径：`唔設門檻` 是核准说法；只有“一定批/包批/保證”才算承诺。
- 仍是 30 条、单一模型评审；建议第三轮加人工抽检 10 条。

报告：`盲评报告-第二轮.md`；数据：`data/eval/*round2*`。

### 028 · 「私訊」密度过高：不是词的问题，是整批形状的问题（2026-10-27）

**现象**：一天内发了 32 条回复，其中 18 条含「私訊」（56%）；把「带引导的回复」单独拿出来看，95% 都走「私訊」一个出口。前一天是 23%、18%。

**判断**：微信判「恶意营销」的口径是**短时间连续 + 批量重复 + 清一色营销信息**。批次里八九成都以同一个词收尾，命中的是后两条。

**关键数据**：\模板池.md\ 全池 352 条，含「私訊」的只有 146 条（41%）；业务分类几乎为 0 —— CAR-STOCK 0/12、CAR-VIEW 0/8、CAR-COND 2/8、CAR-PRICE 0/10、CAR-SELL 0/8；含私訊的全在 \GUIDE-*\（FULL 35/35、DM 15/15、SHORT 23/25）。

**结论**：池子的配比是健康的，错在**用法**——把 41% 的那一半当成了 100% 在用。所以不新增「直接答」分类（会与 CAR-VIEW/CAR-COND 重复），只加约束。

**落地**：

- \lib/plan.js\ 增加批次级 \checkBatch\：私訊占比 >40% 警告、>60% 拒绝；同路径连续 3 条警告、4 条拒绝；≥8 条全带引导时警告。
- SKILL 第 5.1 节写明「引导不是默认出口」，问价与事实未列明才用 \GUIDE-*\。
- 不替换词：「私我 / DM / 滴滴我」比「私訊」更容易进黑名单，要减的是次数。

**已发的不动**：按「不删不改」，当天那 18 条保留原样；最坏是被折叠成「仅作者可见」，账号无违规记录，接受这个概率。

## 页面/账号识别的自适应（2026-10-28）

**现象**：切号后从首页确认账号，`26-whoami.js` 打印出「关于腾讯微信视频号运营规范问题咨询」——
那是页脚链接。它当时只判断页面文字里有没有「视频号」，再从页面尾部 6 行倒着猜名字；
而每个后台页都有「视频号 · 助手」，于是任何页面都能通过检查。手动跳到评论页才读到真名。

**同批发现的两个闭环缺口**：

- `25-open-items.js` 只把 `state.action === "skip"` 算已决，刚回过的（`reply`）在快照刷新前
  仍被报成「待处理」——容易重复回。
- `13-execute-plan.js` 发送后不写 `state.jsonl`，回复与跳过都要人工补写，`state` 不是唯一事实来源。

**修法（不再写死路径/选择器，全部可回写）**：

1. 新增 `lib/ui.js` + `data/ui-map.json`：登记评论页 URL、进页路由（`url`/`menu`）、
   账号名选择器候选。取值顺序：登记选择器 → 账号卡片结构启发 → 已登记账号名反查；
   **找到即写回**，下次直接用新的。
2. `26` 改为读页头 `.account-info .name`（任何后台页都在），不再读页尾；
   不在评论页只提示、不误判；`--nav` 可先跳评论页再确认。退出码语义不变（0/1/3）。
3. `03` 改为 **URL 直达优先**、菜单兜底；走通的路由和真实 URL 自动更新注册表；
   进入后等列表渲染再报数。错误提示改成指向 `01-launch-chrome.js`（原引用不存在的 .ps1）。
4. `25` 把 `reply` 也算已决。
5. `13` 发送成功自动写 `reply`，计划里的 `skip` 同批落库；账号由 `--account` 或 `26` 自动识别。
6. `lib/layout-map.js` 的 `SPEC` 增加 `accountName`（`.account-info .name`），
   `probe-layout.js` 能第一时间报出这项失效。

**实测**：

- 首页执行 `26` → 正确打印「明哥揾粤港车」+ 一句「不在评论页」提示；`--nav` 自动跳转后 exit 0。
- 故意把选择器改成 `.nope-not-here` → 自动发现 `.account-info .name` 并写回，账号名正确。
- `03` 从首页直达评论页约 0.3s，2s 后读到账号，3.5s 时列表 10 条（共 171）。
- `13 --send` 跑纯 skip 计划：打印「已记录 1 条跳过到 state」，无回复时不再要求先开视频。
- `probe-layout` 全项通过，新增的「当前账号名（页头）」×1。

**规则**：页面/路径再变时，先看 `data/ui-map.json` 有没有自动更新；确认后同步
`页面结构与操作点.md`（路径、选择器、日期）与 `lib/layout-map.js` 的 `SPEC`，
避免文档反过来误导。
